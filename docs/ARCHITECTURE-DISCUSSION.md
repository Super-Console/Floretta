# Floretta 产品与技术架构讨论（2026-11）

> 状态：**讨论稿，未实施**。本文只给判断与取舍，不改代码。
> 事实基准：仓库 `Super-Console/Supernode` 提交 `59df26b`（P0 已完成）。

## 0. 先对齐现状（已实现的事实）

不先纠正这点，后面的讨论会建立在错误前提上：

| 已实现 | 内容 |
|---|---|
| 工程 | 一个 Xcode 工程、两个 target（`Floretta-macOS`、`Floretta-iOS` Universal），共享 `Floretta/Shared` |
| 数据模型 | `MindMapDocument`（`formatVersion`、`title`、`roots`）+ `MindMapNode`（UUID、text、note、isCollapsed、children、style） |
| 格式 | **纯 JSON 单文件 `.floretta`**（UTF-8、pretty、sortedKeys），编解码集中在 `FlorettaCodec.swift` |
| 错误处理 | `corrupt` / `unsupportedVersion` / `duplicateID` / `cyclicID` |
| 自动保存 | `Autosave/{AutosaveSession,AutosaveStore,RecoveryPresenter}`，原子写 + 崩溃恢复 |
| 测试 | 20 个用例全绿（模型 12 + 自动保存 8） |
| 未做 | 画布、布局、键盘模型、大纲、格式互通、图标、TestFlight |

**结论**：格式这一层现在只有"一个 JSON 编解码文件 + 20 个测试"，还没有任何画布和附件逻辑。
**所以现在换容器是整件事里最便宜的时刻**；等 P2 格式互通和图片附件做进去，再换就要动导出路径和测试基线。

## 1. 产品定位评价

定位成立，但内部有一个真实张力，必须显式承认：

- "轻量、像原生小工具" 与 "成熟思维导图编辑能力" 在**功能数量**上是对立的；
- 但在**编辑手感**上不冲突——Xmind 的核心价值恰恰不是功能多，而是"手不离键盘就能把结构写出来"。

所以轻量的正确含义是：**功能面收窄，编辑回路做深**。判断标准用一句话：

> 一个功能如果不在"想到 → 敲下来 → 看到结构"这条回路上，就不属于 MVP。

三条非目标建议写死（比写"做什么"更能防走偏）：
不做实时协作、不做云知识库、不做甘特/项目管理；不做"为了对标 Xmind 而存在"的功能。

## 2. Xmind 功能分层：哪些是基础，哪些是商业模式

不要按免费/付费划分，按**它对编辑回路的作用**划分。

### A. 编辑内核（没有就不是思维导图）
节点增删改、同级/子级创建、拖拽重排与跨分支移动、折叠展开、撤销重做、
键盘导航与编辑、画布缩放平移与适配。

### B. 结构表达力（决定"专业感"，但不影响基本回路）
自动布局的多种形态、关系线（非树状连边）、概要、边界、节点备注、
图标与样式、主题。

### C. 输出与交换（决定"能不能带走"）
`.mm` / `.opml` / Markdown / PNG / PDF / SVG。

### D. 商业或规模化能力（Xmind 靠这些收钱，Floretta 不做）
实时协作、演说模式、甘特、云空间、AI 订阅、模板市场、跨端同步服务。

**关键判断**：B 类里只有 **关系线** 和 **备注** 值得早做——它们改变的是"图能表达什么"，
而且都只加数据字段、不加交互复杂度。**多布局**可以晚做，因为它是同一棵树的另一种排布，
后加的代价远小于后加"关系线"（后者要动数据模型）。

## 3. 原生格式：我建议改成 ZIP 容器，而且现在就改

### 候选对比

| 方案 | 优点 | 缺点 | 适配度 |
|---|---|---|---|
| 纯 JSON（现状） | 人可读、Git diff 友好、实现最简 | **装不下附件**；图片只能 base64 内嵌，文件体积膨胀 33% 且 diff 失效 | 只够 MVP 无图阶段 |
| **ZIP + JSON + assets** | 单文件、装得下图片、原子写友好、可扩展多视图 | 二进制，Git diff 不友好 | **推荐** |
| SQLite | 大图查询快、增量写 | 单文件但不可读、diff 废、版本迁移靠手写迁移代码、iCloud 冲突合并更难 | 不适合文档型 |
| XML | 可读、schema 可校验 | 冗长、Swift 侧解析样板多、无优势 | 无理由选 |

### 推荐结构

```
Project.floretta            (zip)
├── document.json           内容树 + formatVersion + 视图状态
├── metadata.json           创建/修改时间、应用版本、下次打开时的默认视图
└── assets/
    ├── image-01.png
    └── image-02.jpg
```

**理由（按权重）**：
1. 附件/图片是迟早要做的，纯 JSON 做这件事的代价是"把图片塞进 base64"，之后一定要推倒重来；
2. 单文件仍然保留"用户能自己管文件"的产品承诺；
3. 原子写用 `FileWrapper` + `NSFileCoordinator` 天然适配；
4. 版本兼容靠 `formatVersion` 字段，不靠容器本身。

**代价要说清**：ZIP 是二进制，**Git 里看不到 diff**。补偿方案：
提供"导出为文件夹（解压版）"和 Markdown 导出；不要为了 Git 友好把容器设计成目录包
（macOS 上 package 目录在微信/邮件里传输会碎，这是更常见的失败场景）。

### 迁移成本（现在 vs 以后）
- 现在：只改 `FlorettaCodec` + 测试基线，约一次提交的量；
- P2 之后：要改 `.mm`/`.opml`/`.xmind` 导出路径、附件存储、恢复逻辑、测试样本。
- **建议**：把编解码抽成协议 `DocumentContainer`（read/write/wrap/unwrap），
  当前 JSON 实现作为其中一种，ZIP 实现作为默认。这样即使你想延后，也不会被锁死。

## 4. 文件优先与系统文档接口

### macOS
- **推荐 `DocumentGroup` + `ReferenceFileDocument`**（SwiftUI 全平台统一），
  而不是 `NSDocument`。理由：三端共用一套文档生命周期，窗口/标签、自动保存、
  版本浏览器由系统接管；`NSDocument` 的优势（多窗口、打印、AppleScript）当前用不上。
- 若后续要做"桌面级多窗口编辑同一文档的复杂场景"，再局部下沉到 `NSDocument`。

### iOS / iPadOS
- 同一个 `DocumentGroup`，但必须实现 **document browser** 体验（文件 App 里可"用 Floretta 打开"），
  以及 `LSSupportsOpeningDocumentsInPlace` / `UIFileSharingEnabled` 配置。
- `FileDocument`（值语义，整份内容装入内存）与 `ReferenceFileDocument`（引用语义，适合大文档）：
  **推荐 Reference 语义**，因为后面要做 5k 节点和附件，值语义每次保存都要复制全量。

### 原子写与安全
1. 写入走 `FileWrapper` → 临时文件 → `replaceItemAt`（macOS）/ `NSFileCoordinator`（协调写入）；
2. 保存失败绝不破坏旧文件（现有 autosave 的原子写策略继续沿用）；
3. 打开时做**资源上限校验**（节点数、深度、解压后大小），防止 zip bomb 与恶意深树；
4. 文件外部被改动：用 `NSFilePresenter` 监听，提示"文件已被其他应用修改"，
   **不要静默覆盖**。

### iCloud 冲突
不自己写同步，也不自己做冲突合并 UI：
- 依赖系统 `NSFileVersion`（冲突版本留在文件旁，系统 UI 可恢复）；
- 我们只做"检测到冲突 → 提示用户选一份"，**不做自动三方合并**。

### 版本管理
不自己做历史。理由：文件在用户手上，历史应由文件系统/iCloud/备份负责；
我们只保证 `formatVersion` 单调递增 + 向后兼容读取（读旧写新）。

## 5. 核心数据模型

```
MindMapDocument
├── formatVersion: Int
├── title: String
├── roots: [Node]           有序
├── relations: [Relation]   非树状连边（A→B，独立于树，按 id 引用）
├── assets: [AssetRef]      文件内资源清单（ZIP 内路径 + 类型 + 尺寸）
└── viewState: ViewState    折叠状态、当前布局、缩放（与内容分离，不弄脏文档）

Node
├── id: UUID（稳定，跨导入导出保留）
├── text / note
├── children: [Node]（有序）
├── style: NodeStyle?
└── collapsed: Bool（视图状态，但随文档保存，避免每次打开全展开）

Relation { from: UUID, to: UUID, label: String? }
```

三条设计要点：
1. **树是唯一真源，关系线是附加层**——关系线不改变父子结构，删节点时级联删相关 relation；
2. **稳定 id 是导入导出的生命线**（`.mm`/`.xmind` 里没有稳定 id 时要生成并记住映射）；
3. **视图状态与内容分离**：折叠、缩放、当前布局不进"内容脏标记"，
   否则拖动一下就算修改，自动保存和撤销都会被噪音污染。

## 6. 布局与渲染

### 架构：布局引擎与绘制分离
- `LayoutEngine`：输入树 + 布局种类 → 输出 `[NodeFrame]`（位置、尺寸、连线路径）；
- `Renderer`：只画 frame，不做决策；两种实现——SwiftUI `Canvas`、AppKit `NSView`（自绘）。
- 三种布局（双侧图、单侧逻辑图、组织结构图）**共用同一棵树**，只是排布算法不同。

### 用什么画
| 选项 | 判断 |
|---|---|
| SwiftUI `Canvas` | 适合起步；大量文本测量与命中测试会碰到瓶颈 |
| AppKit `NSView` / 自绘 | 性能与输入控制最好（Mindscape 就是这条路线）；跨端要写两套 |
| Metal | **不需要**。几千节点的 2D 图形远未到必须上 Metal 的规模，先引入纯属负担 |

**推荐**：`Canvas` 起步 + 文本编辑用系统原生文本控件叠在画布上（不要自己做文本输入）。
只有实测帧率不达标时，再把 Renderer 换成 AppKit 自绘——因为接口已经隔离，换的是实现不是架构。

### 性能的三个真实瓶颈（按出现顺序）
1. **文本测量**：每次布局都重新测量中文文本会卡；必须做测量缓存（按 文本+字号+宽度 键）；
2. **重绘范围**：只重绘脏区域，不要每帧全量重画；
3. **命中测试**：节点多时线性查找会慢，用空间索引（或按布局层级二分）。

### 参考
Mindscape（中文 IME 与折叠控件的处理）、Brainstorm（键盘优先与紧凑布局）、
SwiftFlow（视口变换与命中测试的结构组织）。只借鉴思路，不复制代码。

## 7. 跨平台架构

```
FlorettaCore（Swift Package，无 UI 依赖）
├── Model（文档/节点/关系）
├── Codec（JSON / ZIP / .mm / .opml / .md）
├── Layout（引擎）
├── Commands（增删改移、撤销动作）
└── Persistence（原子写、恢复）

Floretta-macOS  ── SwiftUI 外壳 + 菜单/快捷键 + Canvas/NSView 渲染
Floretta-iOS    ── 同一外壳，iPhone 走"大纲优先"，iPad 走"导图优先"
```

- 共享的是**核心逻辑**，不共享窗口与交互细节；
- 菜单、快捷键、右键菜单用各平台原生 API（Mac 菜单栏、iPad 快捷键、iPhone 长按菜单）；
- Apple Pencil 不做首版；触控先保证"点、拖、双指缩放"三个动作稳。

## 8. 开放格式：分层目标与安全

| 格式 | 规范公开性 | 双向 | 建议阶段 |
|---|---|---|---|
| `.floretta`（自有） | 我们定义 | 双向 | P0 已做（待改容器） |
| FreeMind `.mm` | 公开 XML | **双向** | P2 |
| OPML | 公开标准 | **双向** | P2 |
| Markdown | 公开 | 双向（有损） | P2 |
| XMind `.xmind` | 专有但可解析（zip + content.json） | **仅导入** | P2 |
| iThoughts `.itmz` | 专有（zip + XML） | 仅导入（后期） | 后续 |
| MindManager `.mmap` | 专有（zip + Document.xml） | 仅导入（后期） | 后续 |

三条原则：
1. **不承诺"无损"**，只承诺"可预期的损失"，并在导出对话框里写清楚丢了什么；
2. **每种格式一个独立 codec + 一组真实样本往返测试**，样本进 `Tests/Fixtures`；
3. **安全**：禁止 XML 外部实体（XXE）、限制解压后总大小与节点数、URL 只允许 http/https、
   不执行导入文件里的任何脚本/HTML。

## 9. MVP 边界与顺序（按技术依赖重排）

原方案把"大纲视图"放在 MVP，我同意，并且建议**提前到画布之后立刻做**——理由：
它是同一份数据树的第二个渲染器，实现成本低；而 iPhone 上它几乎是唯一可用的编辑方式。

建议顺序：
1. **P0**（已完成）模型 + 自动保存
2. **P1-a** 画布：平移/缩放/适配/拖动
3. **P1-b** 布局：双侧思维导图（单一布局先跑通）
4. **P1-c** 键盘模型：Tab/Enter/方向键/空格/撤销
5. **P1-d** 大纲视图（与导图同源）
6. **P2** 格式：`.mm` 双向 → OPML → Markdown → `.xmind` 导入
7. **P3 / P4** 图标、TestFlight

**建议调整**：把"容器改成 ZIP"插在 P1 之前（一次提交），否则 P2 做附件时返工。

## 10. 主要风险（按发生概率排）

| 风险 | 说明 | 提前验证方式 |
|---|---|---|
| **中文 IME 在画布上的行为** | 组字时节点宽度、候选框位置、提前折行——Web 类工具全部翻车在这 | 做 200 字中文连续输入的手工用例，录屏对比 |
| **文件协调与 iCloud 冲突** | 两台设备同时改同一个文件，谁赢？静默覆盖等于丢数据 | 两台设备改同一文件，验证"提示而非覆盖" |
| **大图性能** | 5k 节点时的布局与重绘 | 生成 5000 节点压测，记录首帧与拖动帧率 |
| **格式预期落差** | 用户以为"支持 XMind"= 无损 | 导出前明确提示丢失项；写进介绍页 |
| **范围蔓延** | 每加一个"Xmind 也有"的功能都会稀释轻量定位 | 每个新功能对照第 1 节的判断标准 |

## 11. 需要你拍板的 5 个问题

1. **容器**：现在就换 ZIP + assets，还是先 JSON、P2 前再换？（我建议现在换）
2. **macOS 文档层**：统一 `DocumentGroup`，还是 Mac 单独用 `NSDocument`？（我建议统一）
3. **关系线**：进 MVP，还是 V1.1？（我建议进 MVP——它只加数据不加交互）
4. **大纲视图**：MVP 内提前到画布之后，还是按原计划放 MVP 末尾？（我建议提前）
5. **`.xmind`**：只导入，还是也要导出？（我建议只导入，且明说"不保证还原样式"）
