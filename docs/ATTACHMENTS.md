# 附件

状态：生效
建立：2026-11-10

图片、视频、音频，以及塞进导图的其他文件，都按下面办。格式矩阵见 `docs/FORMATS.md`。

## 1. 不设体积上限

以前的「单文件 100MB」「视频 50MB」作废。不再用这两个数拒绝、裁切或降级。

不另定新的产品上限。文件能放进项目，就按原样放。

坏包仍然拒绝：条目畸形、声明的解压大小和实际 inflate 对不上。那是防 zip bomb，不是给正常附件卡体积。

## 2. 大附件插入前确认，且不卡住界面

会把文档撑大的附件，插入前先确认，再写入。确认只读文件大小，不转码、不等压缩，界面不卡住。

确认上必须写清三件事：

- 这个文件有多大
- 字节会原样放进当前项目
- 放进去之后整份文档有多大

用户取消则不插入。

视频和音频每次插入都走同一条确认。只提示体积，不压缩、不改格式。

## 3. 原样字节

禁止有损压缩、降采样、重新编码。导出这份附件必须和插入时的字节一致。

sha256 只用来去重和校验完整性（容器路径 `assets/<sha256>.<ext>`）。哈希相同就复用已有字节，不同就另存。不用哈希当转码的理由。

## 4. 体积要看得见

节点上显示该附件的大小。文档信息里显示附件合计大小。

## 5. 视频和音频

与上面相同：不压缩、不改封装、不改码率、不抽帧。只做体积确认。导出字节与源文件一致。

## 内存

数字以 `docs/PERF-BUDGET.md` 为准。

- 写入附件时的内存峰值 < 32MB，并且不随文件变大。这是内存峰值，不是文件体积上限。
- 打开含 10GB 附件的文档，进程内存增量 < 50MB。附件留在磁盘上，不整包读进内存。
- 缩略图磁盘缓存上限 200MB，按 LRU 淘汰。

## 现状

本文件只定规则，不改容器代码。当前 `ZipContainer` 仍会拒绝单附件超过 16MB、解压合计超过 32MB（见 `docs/STATUS.md`）。那是现在代码里的读取拒绝，不是上面的 32MB 写入内存峰值，也不是产品文件上限。落地时按「不设体积上限」放开读取拒绝，写入峰值仍按 32MB 内存预算做。
